# 0.25s / 0.5s 时序问题摘要

## 问题在哪

系统里有三个不同步的节拍，层级如下：

```
点云 10Hz
  ├─ Explorer 融合:0.5s 节流        ← 节流的真实原因:单次融合+发布 598.9ms,跑不快
  ├─ Explorer 决策拍:0.25s          ← 与融合交错,隔拍看到"没变的地图"
  └─ C++ LocalMapPatch:0.5s → 骨架链(提取+增量+镜像)→ Explorer 侧标签滞后 ~1s+
```

具体四个问题：

1. **融合超支**：单拍 598.9ms(全图 `tolist()` 序列化 + 膨胀集 Python 循环 + 逐格积分)超过 0.5s 周期，感知回调组被连续占满(单核 ~120%)——0.5s 节流不是设计选择，是被性能逼的。
2. **决策拍空转**：0.25s 拍里隔拍看到未变化的地图，每两拍浪费一次全量重算的前置工作；所有消费点被迫加防御(残值门幂等缓存、释放评估去重、ReplanGate revision 上下文)。
3. **标签滞后**：骨架 branch_id 要经 patch→骨架→增量→镜像的链条，比格子旧 ~1s——挂接可能用到过期拓扑(已有“信格子不信骨架”的回退兜底，但时差是根源)。
4. **延迟**：新 frontier 从出现到进入决策，最坏 0.5s(等融合)+ 0.25s(等拍)= 0.75s。

## “心跳”指什么

指 SCAN 在 `/planning/status` 话题上周期性地广播“**我活着，我当前在什么状态**”——即使没有任何新事件发生也照发。这是分布式系统里的标准构件：事件消息(“发生了 X”)只在事情发生时才有，收不到事件分不清“没事发生”还是“对方死了”；心跳则每秒都在响，停了才知道对方死了。

## 现状核验:`planning/status` 现在不是完整的心跳

读代码(`scan_replan_fsm.cpp:2113-2131`)后的准确事实：

- `/planning/status` 的发布**绝大部分是事件驱动**——`PATH_ACCEPTED`、`REACHED`、`BLOCKED`、`VIEWPOINT_LOCAL_REJECTED` 这些，状态一变才发一条(`publishStatus`/`publishReferenceStatus`,`:1528-1545`);
- **唯一的周期性重发**在 WAIT_TARGET 态里，且条件苛刻：只在没有目标、且有一单“已完成待认领”时，每 0.5 秒重发一次 `WAIT_TARGET request_id=...`。注释原话说得很清楚：

```cpp
// REACHED is a one-shot event.  WAIT_TARGET is its durable state and is
// repeated at low rate so Explorer can recover a missed completion.
```

也就是说，这个 0.5 秒重发的存在理由是：**REACHED 是一次性事件，Explorer 万一没收到，永远错过**——所以把“完成”这个事实转成持久的 WAIT_TARGET 态，低频重播，Explorer 任何时候上线/丢包都能补认领。这本质上是“事件可靠性补丁”，不是全状态心跳。

## 这对上一轮建议的修正

我之前说“改用 SCAN 现成的 0.5s 状态心跳做活性判断”——**前提不成立**：现在只在 WAIT_TARGET 一态有周期重发，而执行态(EXEC_TRAJ,恰好是长程任务里时间占比最高的状态)是安静的——没有状态转换就没有任何消息。如果直接把超时改成“5 秒没 status 就算死”，机器人在正常长直道执行时反而会被误杀(执行期本来就没事件)。

所以完整的改法是两步，而不是一步：

1. **把 status 升级为真心跳**：FSM 里加一个小节流(0.5–1s),把**当前状态名**(`EXEC_TRAJ`/`REPLAN_TRAJ`/`GEN_NEW_TRAJ`…)周期性重发——不发任务语义，只发“活着+在哪态”，消息量可忽略；
2. **Explorer 的超时改成活性判断**：心跳在流 → 永远等(哪怕我这一单被 defer 了 60 秒)；心跳停了 5 秒 → 链路死 → 同单重发 → 再失败才放弃。

第 1 步大约十几行(一个节流变量 + 在 execFSMCallback 尾部调用)，第 2 步改 pending 检查十几行，加起来就是你上次问的“超时自救理想化”问题的完整解。

**总结**：心跳 = “周期性广播我活着+我的状态”，与“事件=发生了什么”互补；你的 `planning/status` 目前只有 WAIT_TARGET 一态有重发(为补 REACHED 丢包设计)，要做长程可靠的活性判断，先把它升级成全状态心跳——这也顺手解决了 REACHED 那个“一次性事件怕丢”的老问题。

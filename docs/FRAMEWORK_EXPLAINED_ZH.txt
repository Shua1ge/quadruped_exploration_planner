0. 一句话与一支探险队(先建立整体图景)
--------------------------------------------------------------------------------

一句话: 这套框架把一台探索机器人拆成三个分工明确的管理者
(Explorer / Global / Local),每人只对一类问题拥有最终发言权;每人维护一本用途不同的地图(度量层 / 渔网 / 执行视图);围绕五种生命周期明确的【对象】(任务 / 承诺 / 候选 / 轨迹 / 运动尝试)干活;层与层之间只靠少量【消息】协作。

要治的旧病也在这句话里: 这些边界曾经糊在一起——超时没有归属的权威(A7 类 bug)、一份状态流各人一个解释、一次起步失败被放大成
"整个区域去不了"。重构不是加功能,是把边界立起来。

比喻——一支探险队:
  Explorer  侦察参谋。拿着一本 0.2m 的考察笔记,决定"下一个去看哪里、看到什么程度算看完"。他管【看没看到】。
  Local     带路向导。只管"从这里怎么走过去"。走法都试完了,他报告"这批走法试完了"(EXHAUSTED);但【无权】宣布"这地方永远看不成"。
  Controller 司机。向导选好一条具体走法,司机确认接活(ACK=装载),开车,报告"这趟走完了/中途停了"。注意: 司机说"接了活"【不等于】"送到了"。
  Global    档案管理员。给走过的走廊起名字、记谁连着谁。只管档案,不指挥行动,也不裁决"能不能走"。

三本账(三张图):

  考察笔记 = 度量层(0.2m 证据栅格)——积累的判断: 哪里能走、哪里没看过、看完了没有。
  档案册   = 结构层渔网(~1s 更新)——命名与连接: 这条巷道叫什么、和哪条相连。
  眼前实景 = 执行视图(0.05m 滑窗)——向导只看眼前 10 米,即用即丢。

框架的一个根本选择: 三本账【故意不拼成一张图】。执行要新鲜、决策要保守、身份要稳定,三种需求对"同一处地形"要求不同的分辨率和
不同的更新节奏;拼成一张图等于把三种需求搅在一起(规格 D-2)。

一次普通的动作,把比喻串起来:

  参谋翻笔记,发现一片格子没看过 → 选定区域和路线,给向导下任务  → 向导提出一个起步方案 → 司机确认接活并开车 → 车开过去,传感器
  一路把看到的东西分别记进三本账(各按各的节奏) → 参谋对着笔记核对: 该看的格子真的"看过了"吗 → 看到了,任务关账(SATISFIED),
  选下一个区域;没看到,让向导换一种走法再来。

【审计检查点·第 0 层】
  - 整个系统能否用"谁对哪类问题有最终发言权"来描述?凡是回答成
    "谁处理数据快/谁算法好",说明叙事退回到了性能层,边界没立住。

1. 第一层 · 谁在干活(角色)
--------------------------------------------------------------------------------

这一层回答: 系统里有几个干活的,各自干什么、明确不干什么。

  角色                       一句话                          拥有                                           不拥有
  ────────────────────────────────────────────────────────────────────
  Explorer   记忆与意志        度量层、结构副本、进度解释      身份颁发、
             (看没看到)       器、观测任务生命周期、         渔网权威、
                              任务/失败/冷却记忆、        执行方式与安
                              决策拍流水线                全反射、运动
                                                                              尝试终局
  Global     命名与连接        渔网权威、BranchRegistry    任务意志、
             (这叫什么)       (身份四事件)、锚点、        度量证据、
                              delta/snapshot 分发、       区域可达性
                              失败证据图级固化            终局
  Local      行动与反射        执行视图(0.05m 滑窗)、      观测任务
             (试没试完)       B 样条优化器、A* 重连、      终局、结构
                              安全反射(制动扫掠/硬停)、   身份、长程
                              事实流发布、STOPPING、      记忆
                              运动尝试终局
  ────────────────────────────────────────────────────────────────────
  Controller 不是第四个角色,是 Local 进程内的闭环控制器(closed_loop_controller)。但它的【结果权威】独立:
        轨迹装载结果(ACCEPTED/REJECTED)和已装载轨迹的执行
        结果由它宣布,Local 与 Explorer 都只消费、不代宣布。

为什么把 Controller 单列?因为"轨迹走没走完"和"这批走法试没试完"是两个不同的对象、两种不同的结果,曾经被塞进同一个宽泛状态里互相
污染。权威独立 ≠ 新增进程——规格明确: 进程边界走消息,组件内部走只读快照与有类型的函数接口,【不新增 ROS 节点】。

Local 内部四块(这是"试没试完"的车间):
  a) 目标与候选生成   —— 回答"可以尝试什么"
  b) 统一验证         —— 回答"这个候选是否满足同一合同"(几何/动力学/制动/交接,一套标准,不各开小灶)
  c) 执行协调         —— 回答"Controller 实际装载了哪个版本";它同时是对外执行状态的【唯一汇总出口】
                         (落点 [待填]: Local FSM 侧协调层)
  d) 安全仲裁         —— 决定继续 / 后台替换 / HOLD
现有 FSM 逐步退为编排器,不再新增互相组合的恢复标志。

【审计检查点·第 1 层】
  - 任意挑一个状态写入点: 它是四个角色中的哪个写的?说不出来即为缺陷。
  - 三条具体禁令在代码里成立吗:
      ① Explorer 不得用 exec_time/duration/endpoint_error 复刻
        Controller 的到站判断;
      ② Local 不得用运动结果代替观测完成;
      ③ 任何角色不得把"装载成功"当"执行成功"消费。
  - 有没有为了"理顺边界"而新增 ROS 节点?(设计不走这条路)

2. 第二层 · 记住什么(三张图)
--------------------------------------------------------------------------------

这一层回答: 三本账各记什么、【刻意不记】什么、凭什么各自存在。
审计两张图(或任何新提出的图)最锋利的两问是:
  "它刻意不存什么?"  —— 存了不该存的,就会有人开始依赖它,然后出现第二本账。
  "删了它会怎样?"    —— 答不出独有损失的,是视图不是结构(规格"每图一问"纪律)。

2.1 度量层(Explorer 持有)——考察笔记
  存什么:   0.2m 三态(UNKNOWN/FREE/OCCUPIED)+ 有界证据 evidence
            (int16,±32,占据可逆的机制)+ 每格地形摘要(z_mean/z_cnt)
            + 两样【必须有】的元数据: 每格观测来源标记
            (sensor_observed)与地图 revision。

  地形摘要怎么理解([F1],尚未实现——全仓 grep 无 z_mean/z_cnt,
  是设计项不是现状): 度量层是 2D 的,3D 世界压扁时高度信息丢了。
  但四足需要知道"这格是平地,还是台阶/沟壑/墙"。z 摘要的做法
  极省内存: 传感器射线的测量端点(打在物体上的那个点)落进哪个
  格子,就把该端点的高度 z 计入这格的统计——z_mean 是端点高度
  均值(f16),z_cnt 是端点个数(u8),每格 3 字节。有了它,一格里
  "端点高度都聚在地面附近"读作平地,"端点高度杂乱或整体很高"
  读作台阶或墙。它是"渔网边风险"(这条边要爬坡)与"执行视图
  机体带检查"的供料口(规格 §8:F1 贯通三层)。

  为什么必须是 Explorer 而不是 Local: 轨迹级居中与安全已裁决归
  Local(D-5,preferred-clearance 已实现);但 Local 的滑窗只有眼前
  10×10×5m,任务路线远端的地形它物理上看不到——"这条分支要跨
  一段坎"只有长程层能提前知道,Explorer 才能在分派任务时就绕开,
  而不是让 Local 走到跟前再 EXHAUSTED 一轮。z 摘要影响的是分支级
  取舍,不参与逐格路径搜索,也不是贴墙问题的修复(那是 Local
  优化器 preferred-clearance 的职责,D-5)。

  观测来源标记是干什么的(grid.py:211-213,已实现,现为 uint64):
  每格存"这个格子最后一次被真实传感器观测打到时"的全局版本号;
  全局 revision 每融合一帧传感器数据 +1(grid.py:271)。
  值为 0 = 从未被看过。关键约束: 它只认【观测射线真的落在格子
  上】——代码注释明说不做 robot-centred seeding,"机器人路过
  附近"不等于"看过这格"。
  位宽决策(D-13): 收窄 u64→u32。版本号语义必需——完成判定要
  区分"任务创建前打到"与"任务期间打到",所以不能压成 1 bit
  布尔;但 u64 位宽非必需——融合 4Hz 下 u16 约 4.5 小时即溢出,
  u32 上限约 34 年。收益: 每格 8B→4B(合计 11B→7B),100×100m
  探索面积 11MB→7MB。现实现仍 u64,待改;改后先过完成判定单测。

  关键细节: data 是"结论",evidence 是"依据"。完成判定用的是
            sensor_observed_cells × 任务创建时的 initial_sensor_
            revision(observation_lifecycle.py:37,66-68),【不是】
            "data 变成 FREE"——"格子现在是空的"和"格子被传感器
            看过"是两回事。机制连起来读: 任务创建时拍下当时的
            全局版本号做快照;之后每拍判定时,数目标格里"观测
            来源标记的版本号比快照新"的格子,即【本任务期间】被
            真实看过的格子。用 data==FREE 判定错在哪: FREE 可能
            是任务创建之前的旧观测留下的,data 不携带"谁、何时
            看到";版本戳是观测事件的记录,才是"看过"的证据。
  刻意不存: 3D 结构、语义、原始观测、格子级时间序列、通行性结论。
  谁写:     唯一写者(0.25s 节流单回调,向量化后 1.4ms)。单写者
            是这张图正确性的根基。
  删了会怎样: 系统失去"积累的判断"——执行窗口只记得眼前 10m,
            渔网只有骨架没有格子级证据,探索决策无处落脚。
  权威边界: 它回答"积累了哪些观测证据、还缺哪些信息";【不】回答
            "能不能踩"——地面支撑/坡度/悬空是地形与运动模型的
            输出,不是三态栅格已有的权威。

2.2 结构层渔网(Global 权威持有,Explorer 持副本)——档案册
  存什么:   已知自由空间的连通结构(节点/边)+ 风险语义 + 命名
            (branch_id/region_id/lineage)。节点 ID 用世界坐标
            量化锚定,创建后不移动不重采样;ID 不复用,对象可失活
            退役,保留谱系。
  刻意不存: 格子级证据(度量层的)、任务意志(Explorer 的)、未知
            区域(网只描述已知)、区域可达性结论(那是 Explorer
            经证据分类的裁决)。
  谁写:     Global 单权威,唯一原料是 Local 的 GridMap 切片(P3)。
  删了会怎样: 区域没有稳定名字(退回 IoU 认人)、远距估价退化成
            全图 A*、失败证据无处持久、返航没有分支序列可反向遍历。
  派生视图不驻留: 脊线、区域舱室、路线(分支序列)都按需生成,
            不占内存——能按需生成的不配当结构。
  两层身份(v3.4-a): 网格元素(节点/边/网格单元)可因重建/细化增删;
            分支身份(branch/region)只随真实拓扑语义变化(四事件)。
            数值细化(把粗边拆成短边)不构成 split,不引起区域换名
            或承诺迁移。三角形是构建引擎的内部表示,不对外分发。
  细化=表示修复(v3.4-c): 失败聚集只触发诊断;Global 用新鲜占据
            证据在请求范围内局部细查,确认粗表示遗漏可用连通、
            且有分辨率不足依据,才在预算内加密;细化后无改善要
            记录,防"失败越多图越密"的新循环。验收不是"节点变多
            了",而是"遗漏的接近方案被表达、重复失败减少"。

2.3 执行视图(Local 持有)——眼前实景
  存什么:   0.05m 三维滑窗 10×10×5m(~80MB 固定),log-odds + 膨胀层,
            跟随机器人滑动,窗外清零(即用即丢是特性)。
  权威表述: 它是【执行视图】——有噪声、有延迟、有未知区域的局部
            估计,【不是】"瞬时几何真相"。
  谁写:     SCAN 融合回调 20Hz。
  删了会怎样: 没人能回答"这个 0.05m 体素下,足印撞不撞"——
            0.2m 的度量层和拓扑的渔网都答不了这个问题。
  谁读:     FSM 0.02s 逐样终验、制动扫掠、优化器逐体素查询。

2.4 三张账故意不同步
  同一条巷道,三张图里有三个投影: 执行视图 0.05m 瞬时 / 度量层
  0.2m(0.25s 延迟、持久可逆)/ 渔网(~1s 延迟、结构稳定)。
  时差是特性: 执行要新鲜、决策要保守、身份要稳定。但【每个投影
  必须规定数据年龄上限】([待填])——异步是合理的,过大延迟不是
  架构优势,是待收敛的参数。分歧出现按 fail-closed 处理(作用范围
  见第 7 层),不做统一地图。

  三种"自由"分别命名,不许混称"已知自由空间"(§1.3):
    观测证据自由(Explorer) : "积累的观测说这里没有障碍"——可逆、有迟滞。
    投影通行自由(Global)   : "在指定投影与通行模型下,这里连通"。
    执行合同自由(Local)    : "按当前姿态/速度/合同,这一步可执行"——瞬时、体素级。

【审计检查点·第 2 层】
  - 三张图有没有开始回答同一个问题?两个结构答同一问 = 需要
    对账 = 违反"每图一问"。(历史实证: safe_region/骨架/渔网曾
    三答连通问题,收敛为一张网。)
  - 每张图的写者是否唯一?
  - 有没有往图里塞"判断"而不带依据?(渔网刻意不存可达性结论;
    度量层刻意不存通行性。)
  - 完成判定读的是 sensor_observed × initial_sensor_revision,
    还是"data 变 FREE"?(后者是错的。)

3. 第三层 · 围绕什么转(五个对象)
--------------------------------------------------------------------------------

这一层回答: 系统运转时,"文件"是什么。五种对象,每种讲三件事:
它是什么 / 谁拥有它的终局 / 它住在哪。

  对象        是什么                     终局归属            住哪
  ────────────────────────────────────────────────────────────────────
  任务        一次"去某处看某些格子"    Explorer            Explorer
  (Task)      的意图。                  (SATISFIED,        的任务表
                                        真的看到才算)
  承诺        Explorer 对一个区域       Explorer            Explorer,
  (Commit-    工作集说"我现在在这片     (经承诺转换         挂区域/
   ment)      干活"。                   入口释放)          分支引用
  候选        Local 生成的一个起步      Controller          Local 与
  (Candid-    方案(路线+合同)。         (装载裁决:          Controller
   ate)                                  接受/拒绝装载)     之间,即用
                                                             即弃
  轨迹        Controller 手里一条       Controller          Controller
  (Trajec-    被装载的样条。            (执行完成/中止)
   tory)
  运动尝试    Local 为推进任务发起      Local               Local 的
  (Try)       的一轮运动努力——一轮     (EXHAUSTED:        执行记录
              尝试可能生成多个候选、    候选族穷尽或
              装载多条轨迹。            预算用完)
  ────────────────────────────────────────────────────────────────────

一句话记住分工:
  Explorer   管"看没看到"(任务),
  Local      管"试没试完"(尝试),
  Controller 管"这条轨迹走没走完"(轨迹),
  Global     管"这地方叫什么"(身份)。
  任何人都不替别人下结论,也不替别人改结论。

两个容易踩坑的边界:

(a) 任务是独立对象,不是图上的属性(v3.3-e)。
    任务可以引用区域或分支的 ID,但图上删节点、拆分支、合并谱系,
    都【不会】改变任务的终局。图上只挂引用/摘要,终局载体是任务
    对象本身。反过来也成立: 任务终局只能由 Explorer 写,没有
    "图变了所以任务算失败"的隐式路径。

(b) 三个"图"不共用一个字(§5):
    底层是【允许有环的空间连接图】(真实走廊会绕回);
    身份谱系关系形成【DAG】(split/merge 的历史);
    承诺展开生成【树形视图】。
    "子树"只是派生视图——展开它不改变底层连接,也不改变谱系。
    审计时的问法: 承诺代码有没有顺手改了连接关系或谱系?

【审计检查点·第 3 层】
  - 任意挑一个对象: 它的终局只能由谁写?有没有第二条写入路径
    (超时兜底、异常分支、"以防万一"的清理逻辑)?
  - 图操作(删节点/拆分支/merge)会不会隐式改变某个任务的终局?
  - 一轮运动尝试里,候选被拒一次就被当成"穷尽"了吗?
    (EXHAUSTED = 候选族穷尽或预算尽,不是"第一次被拒"。)
  - 有没有对象的关键字段(如目标集)需要从终局反推?
    (终局不知道目标集是什么——重启恢复从任务快照来,见第 7 层。)

--------------------------------------------------------------------------------
4. 第四层 · 谁说了算(权威阶梯与唯一来源)
--------------------------------------------------------------------------------

这一层回答: 冲突时听谁的,以及"每问一权威"到底约束什么。

4.1 权威的定义(审计时最容易误用的一条,§1.1)
  "每问一权威"约束的是【某个明确状态的写入权与终局裁决权】,
  【不是】要求其他层完全不能判断、不能维护状态:
    - Controller 判断"这条轨迹走完了" ≠ 它维护了第二本观测账本;
    - Local 判断"这批起步候选都不安全" ≠ 它越权判断"这个区域
      不可观测"。
  真正的禁令是: 不同对象的结果,不得通过 FINISHED/BLOCKED/REACHED
  这类【宽泛名字】混在一起,再被另一层解释成更大的失败或完成。
  审计时看到宽泛枚举先问: 它混了几种对象的结果?

4.2 五问权威表(按对象生命周期)
  对象            生命周期权威      终局裁决            裁决依据
  ──────────────────────────────────────────────────────────────
  观测任务        Explorer          SATISFIED/换站位/  真实观测证据
                                    切任务             (目标格解析)
  运动尝试        Local             EXHAUSTED          统一验证+安全仲裁
  执行轨迹        Controller        SUCCEEDED/REJECTED ACK 事务
  区域可达性      Explorer(经证据) 同一转换入口        证据分类(§5)
  分支身份        Global Registry   extend/split/      图拓扑+迟滞确认
                                    merge/vanish
  ──────────────────────────────────────────────────────────────
  违例判定: 任何状态转换必须能指出它的权威是谁;找不到权威的转换
  = 设计缺陷(A7 实证: goal_timeout 没有归属权威,承诺悬空)。

4.3 事实唯一来源表(§7,审计的核心工具)
  事实                                唯一来源
  ──────────────────────────────────────────────────────────────
  候选装载结果(ACCEPTED/REJECTED)    Controller(ACK 事务)
  已装载轨迹的执行结果               Controller
  当前运动状态(STOPPING/STOPPED)    Controller(实测)
  起步候选安全判定                   Local(统一验证+安全仲裁)
  运动尝试终局(EXHAUSTED)           Local
  观测任务终局(SATISFIED)           Explorer
  区域/分支身份                      Global Registry
  ──────────────────────────────────────────────────────────────
  "不新增话题"不是正确性标准,【唯一来源】才是(§4.0)。

4.4 汇总出口(v3.3-a)
  执行协调组件(Local 侧)是对外执行状态的【唯一汇总出口】:
  Controller 与 Local 各自拥有自己产生的结果,汇总组件只【归并
  转发】,不重新裁决——无权把"尝试穷尽"改写成"任务失败",也无权
  把"轨迹走完"改写成"任务完成"。两份状态交替到达由它归并;
  Explorer 不自行解释两份并行状态流。

4.5 正交维度(v3.3-a)
  当前运动状态(STOPPING/STOPPED)与对象终局(SUCCEEDED/EXHAUSTED/
  SATISFIED)是两个【正交维度】,不塞进单一互斥枚举——
  "已停稳 + 轨迹结束 + 任务未满足"是合法组合,必须可直接表达。
  审计问法: 如果表达不了这个组合,是枚举设计错了,不是场景错了。

【审计检查点·第 4 层】
  - 任意字段能否在唯一来源表里找到、且只找到一行?
  - 代码里还有没有 FINISHED/BLOCKED/REACHED 类宽泛名字在混合
    不同对象的结果?
  - 汇总组件有没有"顺手"改写别人的结果?(归并 ≠ 裁决)
  - 任意一次状态转换能否指出它的权威?找不到 = 设计缺陷。
  - "停稳+轨迹结束+任务未满足"能表达吗?

--------------------------------------------------------------------------------
5. 第五层 · 怎么说话、说多快(协议与时间尺度)
--------------------------------------------------------------------------------

这一层回答: 层与层之间走什么消息,每条消息的规矩是什么,各环节
允许多慢。

5.1 四条协议(层间只走消息;三张图之间不存在直接读写)

  P1 任务下发(Explorer → Local)
    载体:   /observation_task(task_mode)或 /initial_path(兼容模式)
    内容:   task_id/version · region/branch 引用 · coarse_route ·
            corridor_radius · 剩余 target_cells(过滤后) · 建议站位
    纪律:   "单号挂起"只约束【请求-响应对】——同一任务同时只有
            一个未决请求。它【不】禁止前一任务收尾时并行准备后继
            任务;后继准备完成也【不】自动授权执行(授权独立裁决)。
            5s 超时自救;超时自救不触碰承诺。
    审计问: "一单在飞"有没有被实现成"禁止后继准备"或
            "准备完就自动执行"?两种都是收窄前的旧语义。

  P2 执行事实流(Local → Explorer)
    载体:   ExecutionState 扩展(不新增话题;0.1s 节流,已含
            request_id/task_id/task_version/trajectory_id 四 ID)
    扩展:   blocked_segments[] · holding{reason} ·
            braking{eta_s, dist_m}[待填 stop-probe] ·
            state 枚举扩展 STATE_STOPPING/STATE_STOPPED
    纪律:   三级裁决归位——Controller 宣布候选装载结果
            (ACCEPTED/REJECTED,ACK 事务)【与】已装载轨迹的执行
            结果;Local 宣布运动尝试 EXHAUSTED;Explorer 宣布
            观测任务 SATISFIED。
    关键语义: ACK = 候选【装载】结果,证明"司机接了活",
            【不】证明运动成功完成。
    终局与缓冲: 见第 7 层(保留语义/满载五规则/重启恢复)。

  P3 结构喂入(Local → Global)
    载体:   /grid_map/local_map_patch(0.5s)
    内容:   0.2m 占据切片 + revision
    纪律:   渔网的【唯一原料】;patch 不携带任何身份/语义。
    审计问: 渔网还有没有第二个原料来源?(曾经写错成 Explorer
            栅格供料,v3.1 改正——两个来源 = 两个真相。)

  P4 结构分发(Global → Explorer)
    载体:   topology_delta / topology_snapshot
    内容:   节点/边增删改 + branch/region 属性 + 谱系事件[草案]
    纪律:   Explorer 副本【纯消费】,不推断身份。
    审计问: 副本有没有开始自己猜身份?(比如 IoU 匹配造 ID。)

5.2 三拍时间尺度(v3.3-f)
    决策拍 0.25s(Explorer)/ 执行拍 0.1s(事实流)/ 结构拍 ~1s(渔网)。
    各拍须规定允许的数据年龄与计算预算([待填])。
    尺子: "异步更新是合理的,过大延迟不是架构优势。"
    审计问: 看到"等它自己同步"或"反正最终一致"的代码,先问
            这一拍的数据年龄上限是多少;答不出 = §9 待填项,
            标记为审计发现。

5.3 停车期间的时序约束(STOPPING 三分,v3.1-g)
    停车期间: 继续计算下一任务 ✓ / 准备下一运动候选 ✓ /
              授权候选开始执行 ✗(由执行侧按实测状态与安全认证决定)。
    不把正常减速当成执行停滞,不启动不兼容的运动。
    STOPPED 确认靠【实测】速度/角速度/必要姿态条件;ETA 是预测,
    不得作为停稳判据。

【审计检查点·第 5 层】
  - 每条消息的每个字段,能否回溯到唯一来源表的某一行?
  - 有没有把 ACK 当"执行成功"消费的路径?
  - 各拍的数据年龄上限定了没有?
  - 停稳判据是实测还是 ETA?
  - "一单在飞"有没有被扩大成"禁止准备后继"或"自动授权"?

--------------------------------------------------------------------------------
6. 第六层 · 一次任务的一生(动态主线)
--------------------------------------------------------------------------------

前五层是静态结构,这一层通电: 一条时间线走完一次任务的常态。
每步一行;逐步展开(每步的谁/动什么/过哪道门/出岔路走哪)在
PROCESS_WALKTHROUGH §3-§5。

  T0  决策拍: Explorer 读度量层,发现未满足的信息需求 → 选区域、
      拓扑路线、允许观测范围。
  T1  下发任务(P1): 任务对象建立;请求-响应对开始。
  T2  Local 生成候选 → 统一验证(几何/动力学/制动/交接,同一合同)。
  T3  Controller 装载裁决: ACK(ACCEPTED=接活 / REJECTED=拒装)。
      【注意】REJECTED 不是穷尽,回到 T2 换候选。
  T4  执行: 事实流 0.1s;传感器 20Hz 喂执行视图、0.25s 喂度量层、
      0.5s 喂渔网——三本账各按各的节奏记账,互不等待。
  T5  执行结果: Controller 宣布(完成/中止)。交接前,旧前缀持续
      执行到【合法切换点】,前提是期间仍然安全(新观测发现障碍
      必须允许提前打断)。
  T6  观测判定: Explorer 用 sensor_observed × initial_revision
      读数。
        够了   → SATISFIED,任务关账 → T7。
        不够   → 换站位/换起步假设,回到 T2(同一任务,新一轮
                 运动尝试;每次记录"相较上次改变了什么")。
  T7  完成 → 承诺转换入口 1 → 后继任务【并行准备】(不互相阻塞:
      前一任务收尾不挡后继准备,后继准备完不自动执行)。
  T8  交接: 候选已装载 + 到达安全让位点 + 授权转移,三条件齐 →
      版本化切换 → 旧对象退役,终局入缓冲(可重复传输,副作用
      恰好一次)。

  出岔路(三条过程,详见 PROCESS_WALKTHROUGH):
    起步失败 → 过程B: 拒绝分类 → 同任务有界重试(记录改变了什么)
               → 候选族穷尽或预算尽才 EXHAUSTED → 证据入图(三要素)
               → 区域保留在候选列表。
    取消     → 过程C: 承诺转换入口 3 → 三道闸(版本失效/任务栅栏/
               授权撤销)→ 命令归零 → 实测停稳 → 迟到消息被版本
               栅栏拒绝,无副作用。
    正常交接 → 过程A: 即 T0-T8 全程,验收读数 B1a/B1b/B2。

【审计检查点·第 6 层】
  - 时间线上任何一步到下一步,【条件】是什么?"没有条件就往下走"
    的转换都是隐患。
  - 每个对象的建立时刻和关账时刻,能否在时间线上指出?
  - T6 的"不够→回到 T2"里,新一轮尝试有没有记录"相较上次改变
    了什么"?(新请求 ID 不算改变。)
  - T8 的三条件,代码里是【与】关系还是"满足其一就切"?

--------------------------------------------------------------------------------
7. 第七层 · 出错了怎么办(失败、缓冲、恢复)
--------------------------------------------------------------------------------

这一层回答: 拒绝怎么分类、失败证据管多宽、终局消息丢了/重复了/
消费者掉线了怎么办。

7.1 拒绝必须分类(§1.6,禁止"自动升级")
  Local 可拒绝执行,但每次拒绝必须有分类,分类决定去向:
    实际占据反证   → 传感器看到的与规划假设冲突 → 上报 blocked
    地图过期       → 更新可消除分歧 → 就地等待/重查,不上报
                     【但必须报告等待原因与退出条件】(重试上限/
                     revision 前进/上层超时)——不是"完全不上报"
    姿态变化       → 估计漂移 → 触发局部重查
    规划预算耗尽   → 上报 EXHAUSTED(运动尝试终局)
    运动合同不适用 → 上报合同级失败(如 STOPPING 期间拒绝新轨迹)
  一条总纲: 一次局部拒绝【不】自动改变持久拓扑,【不】自动把区域
  判成不可观测。

7.2 EXHAUSTED 的真语义(v3.3-d)
  单候选拒绝 ≠ 尝试穷尽。EXHAUSTED = 候选族穷尽【或】预算尽。
  有界重试,每次记录"相较上次改变了什么"——换了新请求 ID 不算
  改变。换站位不一定有用: 失败证据约束的是出发连接时,换更远的
  目标照样撞同一段。

7.3 失败证据三要素与作用域(§5)
  挂到图上的约束必须带: 来源(哪个任务/哪次尝试)、适用运动条件
  (哪个站位/合同/起步)、撤销条件(什么观测出现时失效)。
  作用域由【证据类型】决定,不由存储位置决定:
    一次起步失败 → 约束该站位/该合同的再次起步
    路线级阻断   → 约束分支(须路线级证据;承诺转换 5)
  把起步失败存到图上,【不等于】Global 有权宣布整条分支不可通行。
  撤销: 满足该证据【自身】撤销条件时撤销——"有新帧"不等于
  "原障碍消失",别处地图更新不清当前出发方向的失败记录。

7.4 终局缓冲(v3.3-b)
  保留语义: 终局保留到 (a) 被确认消费,或 (b) 被【同一对象】的
  替代结果/显式失效取代。替代只在同一对象内发生(轨迹终局被轨迹
  终局取代,任务终局被任务终局取代)——不存在 Explorer/Local/
  Controller 之间的跨角色"更高权威覆盖"(该表述已作废)。
  满载五规则(缓冲有界 [待填 条数]):
    ① 当前活动对象及其终局【常驻】(重启对齐的锚);
    ② 旧记录按明确规则压缩([待填]: 按对象保留最后终局);
    ③ 消费者落后超过保留范围 → 发布显式【缺口事件】,不静默丢;
    ④ 消费者恢复时以当前对象快照重新对齐;
    ⑤ 记录消费【永不阻塞安全停车】。
  B6 副作用恰好一次: 同一终局可以重复传输,但对决策的副作用恰好
  一次——靠"消费确认 + 对象 ID + 终局 ID"去重,【不】靠
  "收到过就忽略"(那会把合法重复和真重复混在一起)。
  Explorer 重启: 执行状态只恢复【运动上下文】(在动/停稳);观测
  目标集与承诺从 Explorer 自己的任务快照恢复,不从最近终局推导
  ——终局不知道目标集是什么。

7.5 fail-closed 的作用范围(v3.3-f,拒绝"一处过期全身停车")
    当前执行合同不满足 → 停车/不起步(合同范围内,照旧)
    远处结构信息过期   → 限制依赖它的路线选择与跨分支动作;
                         【不】自动停掉已认证的安全前缀
    地图过期就地等待   → 不生成持久阻断证据,但必须报告等待
                         原因与退出条件
  配套的 D-5 收窄: 退役的是全局对局部【精确几何的强制控制】,
  【不是】所有 clearance/风险信息——Explorer 保留粗略风险估价
  用于接近通道取舍,否则任务会被频繁送到贴边/狭窄位置。

7.6 失败记忆与表示修复(v3.4)
  证据锚世界坐标: 失败段几何+接近方向+适用运动条件+撤销条件是
        证据本体;边 ID 只是索引,不是存在依据。结构重建/细化时
        按空间范围重新挂接——只挂到失败段实际覆盖的边,不复制
        全量约束(局部失败不许扩成整段受限),不因旧边删除而丢失。
  与结构分离: 约束 overlay 不改连接结构/身份/谱系;snapshot
        替换的是结构副本,【不动】约束层;本地待确认证据按
        evidence_id 去重转正(与 B6 同构)。
  两级时序: 【立即应用约束】(当轮生效,不等 Global)/【异步修复
        表示】(诊断后才细化,可选分支非必经层)——不预设毫秒/
        秒级,预算+实测定。
  恢复分流: "图表达不出连接"(走表示修复)≠"Local 生成不出轨迹"
        (采样/候选形态/允许域/认证问题,在 Local 组件处理)——
        两个问题两种修法;Local 候选生成不以渔网枚举绕行为前提。
  本节检查点: 证据迁移有没有扩大作用域?细化有没有"无改善记录"?
        执行失败有没有被直接写成结构变更(而非经核验的占据反证)?

【审计检查点·第 7 层】
  - 每条拒绝路径有没有分类标签?没有分类 = "自动升级"复发。
  - 证据的使用有没有超出自身作用域?(站位级证据杀掉整条分支
    = 违反作用域纪律。)
  - 证据的撤销条件是它自己的,还是"来了新数据就撤"?
  - 缓冲满载的代码路径上,安全停车会不会等消费?(应该永不。)
  - 去重键是什么?"收到过就忽略"是错的;应是消费确认+对象 ID
    +终局 ID。
  - Explorer 重启后,目标集从哪来?(任务快照;从最近终局推导
    = 错。)

8.2 三条端到端演练(把验收钉到可证伪的场景)
  演练A 正常完成→滚动交接: 钉 B1a/B1b(两段延迟)、B2(存续与
        停顿归因)、状态流无双头解释。链: SATISFIED → 转换入口 1
        → 后继准备与下发 → 候选装载 → 旧前缀执行至合法切换 →
        版本化交接 → 旧对象退役。(逐步展开: PROCESS_WALKTHROUGH §3)
  演练B 起步失败→区域保留: 钉 B3/B4。链: 候选被拒 → 分类记录 →
        同任务有界重试(每次记录改变了什么)→ 穷尽才 EXHAUSTED →
        证据入图(三要素,作用域=站位/合同)→ 区域仍在候选列表;
        失败信号: Frontier 永久消失,或换站位后重复同一段失败
        出发连接。(§4)
  演练C 取消→迟到消息: 钉 B5。链: 取消 → 转换入口 3 → 三道闸 →
        命令归零 → 实测停稳 → 迟到 ACK 被版本栅栏拒绝且拒绝
        无副作用。失败信号: 旧执行被重新授权/旧候选被重新接受/
        持续非零命令。(§5)

8.3 阶段退役表(§12.3)
  每阶段以"替换旧职责、退役旧入口"验收——【旧职责不退役,新职责
  不算落地】。审计进度时先问: 这一阶段对应的旧入口退役了没有?
  (例如: 进度解释器阶段对应"REACHED/STALLED 语义事件退役";
   STOPPING 阶段对应"soft-hold 布尔族退役"。)

【审计检查点·第 8 层】
  - 每条验收是否可证伪(失败信号写得出来)?
  - 停顿有没有归因手段(原因字段+时间记录),还是靠位移猜?
  - 当前实现处在退役表哪一行?旧入口退了没有?

9. 第九层 · 框架自己承认没定的事(待填空间)
--------------------------------------------------------------------------------

审计者最需要知道框架在哪里【诚实地说了不知道】。以下全部来自
规格 §9,写剖析文档时不替它填:

  [待填] 终局缓冲上限与满载压缩规则
  [待填] B1a/B1b 延迟阈值(两段分别实测后定)
  [待填] 执行协调组件的进程内落点(Local FSM 侧协调层归属与接口)
  [待填] 各拍(决策/执行/结构)数据年龄与计算预算
  [待填] 起步重试预算(次数或时间上界)
  [待填] stop-probe 标定(真实制动延迟/减速度/瞬态——现用拍的
         模型 0.32 m/s² 与 0.30s 延迟)
  [待填] merge 事件规则细节(环路闭合 ≠ lineage 自动统一)
  [待填] 走廊域参数 R / region churn 基线 / 兄弟摘要刷新策略 /
         前瞻小图规格 / 多机器人身份上收触发条件

(写死的超时、拍脑袋的缓冲条数),应作为审计发现登记——它们
本该走实验标定或明确设计。
